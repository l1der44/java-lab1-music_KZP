# Звіт до лабораторної роботи № 5

## 1. Тема, номер і варіант
- **Дисципліна:** Кросплатформні засоби програмування
- **Лабораторна робота № 5:** Параметризоване сховище, винятки й CSV-експорт у Java-проєкті
- **Варіант:** 13 — Музична фонотека (`TrackRecord`)
- **Середовище:** Windows, Java 21, JUnit 5.12.2, VS Code

## 2. Мета роботи
Замінити пряме зберігання записів у списку на типобезпечне параметризоване сховище `Repository<T>`, реалізувати власний checked-виняток `DataStorageException` зі збереженням першопричини (`cause`), описати CSV-стовпці анотацією `@CsvColumn`, створити універсальний рефлексивний експортер `CsvExporter` і автоматний парсер `CsvParser` із явним кодуванням UTF-8, а також довести цілісність даних тестом `round-trip`.

## 3. Стан до і після цієї роботи
- **До (ЛР 1–4):** дані фонотеки оброблялися в пам'яті у `List<Track>` через `MusicManager` та аналізувалися запитами Stream API у `MusicReport`.
- **Після (ЛР 5):** додано узагальнене сховище `Repository<T>`, модель `TrackRecord` з анотаціями `@CsvColumn`, універсальний експортер `CsvExporter`, парсер `CsvParser`, виняток `DataStorageException` та набір тестів `StorageExportTest`. Усі попередні класи та тести збережено без змін.

## 4. Repository<T>
Параметризований клас `Repository<T>` працює без raw types і забезпечує перевірку типів на етапі компіляції:
- `add(T item)` — додає елемент після перевірки `Objects.requireNonNull`;
- `all()` — повертає незмінний знімок колекції через `List.copyOf(items)`, що унеможливлює зовнішню модифікацію внутрішнього списку;
- `find(Predicate<? super T> condition)` — виконує фільтрацію записів за предикатом.

## 5. Модель даних (Варіант 13)
Клас `TrackRecord` містить 5 незмінних (`final`) полів:
- `performer` (`String`) — `@CsvColumn("виконавець")`
- `title` (`String`) — `@CsvColumn("назва")`
- `album` (`String`) — `@CsvColumn("альбом")`
- `durationSeconds` (`int`) — `@CsvColumn("тривалість")`
- `genre` (`TrackGenre`: `ROCK`, `INDIE`, `POP`, `ELECTRONIC`, `ACOUSTIC`) — `@CsvColumn("жанр")`

Ключ ідентифікації `round-trip`: `performer + title`. У конструкторі перевіряються інваріанти (непорожні рядки, додатна тривалість, не-null жанр). Реалізовано узгоджені методи `equals` та `hashCode` за всіма полями.

## 6. @CsvColumn
Анотація `@CsvColumn` оголошена з `@Retention(RetentionPolicy.RUNTIME)` та `@Target(ElementType.FIELD)`. Єдиний параметр `String value()` задає назву стовпця в CSV. Порядок стовпців детермінований шляхом сортування полів за Java-іменами: `album`, `durationSeconds`, `genre`, `performer`, `title`.

## 7. Рефлексивний експортер (CsvExporter)
`CsvExporter.write(Path path, Class<T> type, List<? extends T> records)` не містить жодної прив'язки до `TrackRecord` чи іншого предметного класу:
1. Отримує оголошені поля через `getDeclaredFields()` і фільтрує ті, що мають `@CsvColumn`.
2. Сортує поля за `Field::getName` для стабільного порядку стовпців.
3. Відкриває доступ через `field.trySetAccessible()`.
4. Формує заголовок зі значень `@CsvColumn` навіть для порожнього списку `records` (завдяки параметру `Class<T>`).
5. Екранує значення з комами, подвійними лапками або перенесеннями рядка та записує файл через `Files.writeString` із `StandardCharsets.UTF_8` і `StandardOpenOption.TRUNCATE_EXISTING`.

## 8. Формат CSV
- **Кодування:** `UTF-8`
- **Фактичний заголовок:** `альбом,тривалість,жанр,виконавець,назва`
- **Приклад рядка з екрануванням коми:** `"Там, де нас нема",269,ROCK,Океан Ельзи,"Там, де нас нема"`
- **Приклад рядка з екрануванням подвійних лапок:** `Live,275,ACOUSTIC,Один в каное,"Човен ""Акустика"""`

## 9. Імпорт і перевірка round-trip
`CsvParser.parseDocument(String text)` реалізовано як скінченний автомат із прапорцями `quoted` та `quoteClosed`, що дозволяє коректно відрізняти кому або символ нового рядка всередині лапок від роздільників полів та записів. Відновлення об'єктів виконується методом `TrackRecord.fromFields(List<String>)`. Порівняння `repository.all().equals(restored)` повертає `true`.

| :--- | :--- | :--- | :--- |

| Рефлексія | Клас без анотованих полів або закритий доступ до поля | `DataStorageException` | Пояснення відсутності `@CsvColumn` або доступу |

## 11. Тестування
У `StorageExportTest` (JUnit 5) перевірено:
- додавання, предикатний пошук та незмінність знімка `Repository<T>`;
- наявність `@CsvColumn` у runtime через рефлексію;
- експорт і `round-trip` для 3 записів із комами, лапками та перенесеннями рядків (4 фізичні записи CSV включно із заголовком -> 3 відновлені об'єкти);
- універсальність `CsvExporter` на сторонньому класі `PlaylistNote`;
- експорт порожнього списку (1 рядок заголовка);
- збереження `cause` (`NumberFormatException`, `IllegalArgumentException`, `IOException`) у `DataStorageException`.
Усі тести ЛР 3–4 (`TrackTest`, `MusicReportTest`) виконуються разом із новими без помилок.

## 16. Відповіді на контрольні питання
1. **Яку проблему розв'язує параметр типу в Repository<T>?** Забезпечує типобезпеку на етапі компіляції та дозволяє використовувати один клас сховища для різних типів даних без ручного приведення типів (`cast`).
2. **Чим параметризований клас відрізняється від raw type?** Параметризований клас (`Repository<TrackRecord>`) перевіряє типи під час компіляції, тоді як raw type (`Repository`) вимикає перевірку узагальнень і може призвести до `ClassCastException` під час виконання.
3. **Навіщо Predicate<? super T> у методі пошуку?** Принцип PECS (Consumer Super): дозволяє передати предикат, написаний для батьківського типу (наприклад, `Predicate<Object>`), для фільтрації об'єктів типу `T`.
4. **Чому all() має повертати незмінний знімок?** Щоб зовнішній код не міг змінити внутрішній список сховища в обхід методів класу (інкапсуляція).
5. **Що таке checked exception і коли він доречний у цій роботі?** Це виняток, який компілятор зобов'язує обробити або оголосити в `throws`; доречний для зовнішніх операцій вводу-виводу та парсингу (`DataStorageException`), де помилку можна коректно обробити.
6. **Для чого зберігати cause власного винятку?** Щоб не втратити першопричину збою (`IOException`, `NumberFormatException`) під час налагодження та аналізу стектрейсу.
7. **Чим Path і Files кращі за складання шляху рядком?** `Path.of(...)` автоматично використовує правильний роздільник директорій для поточної ОС (`\` у Windows, `/` у Linux/macOS).
8. **Чому кодування потрібно задавати і під час запису, і під час читання?** Різні ОС мають різні стандартні кодування (наприклад, Windows-1251 проти UTF-8), тому явне `StandardCharsets.UTF_8` гарантує коректне відображення кирилиці скрізь.
9. **Що роблять @Retention(RUNTIME) і @Target(FIELD)?** `RUNTIME` зберігає анотацію у байткоді для доступу через рефлексію під час виконання; `FIELD` дозволяє ставити анотацію лише над полями класу.
10. **Чому анотація не виконує експорт сама?** Анотація — це лише пасивні метадані; логіку їх зчитування та обробки виконує зовнішній код (`CsvExporter`).
11. **Чим getDeclaredFields() відрізняється від отримання публічних полів?** `getDeclaredFields()` повертає всі поля, оголошені безпосередньо в класі (включно з `private`), тоді як `getFields()` — лише `public`-поля (разом з успадкованими).
12. **Навіщо перевіряти trySetAccessible()?** Щоб отримати право читати значення `private`-полів через рефлексію та коректно обробити відмову доступу у модульному середовищі Java.
13. **Чому порядок полів для CSV потрібно зробити детермінованим?** JVM не гарантує фіксований порядок полів у `getDeclaredFields()`, тому сортування за іменем гарантує однаковий порядок колонок при кожному запуску.
14. **Чому split(",") не підходить для загального CSV?** Він помилково розіб'є текстове значення, яке містить кому всередині подвійних лапок (наприклад, `"Там, де нас нема"`).
15. **Як екрануються кома, лапка й перенесення рядка в CSV?** Усе поле береться в подвійні лапки `"..."`, а кожна подвійна лапка всередині тексту подвоюється (`""`).
16. **Чому порожній список потребує окремого параметра Class<T>?** Через стирання типів (type erasure) у Java із порожнього `List<?>` під час виконання неможливо дізнатися тип елементів, щоб побудувати рядок заголовка.
17. **Чим універсальний експортер відрізняється від предметного fromCsv?** Експортер працює з довільним класом через рефлексію і пише рядки, а `fromCsv` знає правила валідації та типи конкретного класу (`int`, `enum`).
18. **Які рівні помилок розрізняє програма?** Помилки моделі (`IllegalArgumentException`), формату CSV, значень полів, файлової системи та рефлексії (`DataStorageException`).
19. **Що доводить тест round-trip?** Що цикл «об'єкт -> CSV -> об'єкт» відбувається без втрати чи спотворення даних.
20. **Чому виняток не можна поглинати порожнім catch?** Це приховує факт збою, маскує пошкоджені файли під порожні результати й унеможливлює діагностику.

## 17. Висновки
У межах лабораторної роботи № 5 застосунок «Музична фонотека» отримав параметризоване сховище `Repository<T>`, рефлексивний механізм експорту за анотацією `@CsvColumn`, стійкий до спецсимволів CSV-парсер та обгортку помилок `DataStorageException` зі збереженням першопричини. Сформований CSV-файл у кодуванні UTF-8 має чітко визначений заголовок і структуру, що робить його готовим вхідним набором даних для наступного програмного блоку.
